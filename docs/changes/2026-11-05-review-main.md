## 审查发现

### P1 登录与写入口缺少限流

OPS-12 要求写入和高成本入口按主体限流，运维基线规定普通写入暂定每用户 60 次/分钟、登录额外按来源限制。当前 `app/api/auth.py:117` 直接调用认证服务，`app/services/auth.py:40` 每次请求均进入查询和口令校验。API、服务及 Compose 未配置相应限流。

在 Flask 真实请求入口注入拒绝登录的认证替身，同一来源连续发出 65 次合法格式请求，全部到达认证服务，均为 401，没有 429。此证据验证入口没有拦截，未在真实账号或共享数据库尝试口令。缺少限流使反复认证可以持续消耗哈希资源，也不符合现行写入配额规则。需明确来源及主体配额、窗口、并发行为和 429/1600 契约，并补边界及失败无副作用回归。

### P2 场景追溯门禁只覆盖骨架

`scripts/check_layout.py:72` 只读取 skeleton-runtime 和 skeleton-access，场景编号正则及测试发现也仅覆盖两位前缀和 `test_*.py` 中的函数名。认证、资料和后续能力的必测场景不受该映射检查约束，真实依赖验证中的 `auth_runtime.py` 也没有显式场景登记。

在临时副本给认证规格追加无对应用例的 AUTH-F99，调用同一 `check_scenarios()` 仍返回空错误列表。这表示现有测试成功和 OpenSpec 结构合法，不能证明全部已实现能力的场景均受门禁约束。按 TEST-02 和 CK-01，需为已实现能力建立明确的能力、场景、用例及执行入口映射，并验证缺场景时非零退出。在规划中的业务场景须区分尚未实现，避免把全部未来场景直接设为当前必测项。
