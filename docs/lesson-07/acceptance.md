## 运维设置必需检查

远程分支接口本轮返回 `protected=true`，但 `required_status_checks.enforcement_level=off`、`contexts=[]`、`checks=[]`。这是当前缺口；不能把“开启保护”或“CI 为绿”写成“失败已禁止合并”。

1. 有管理权限的运维在 GitHub 仓库 Settings → Branches 中编辑适用于 `main` 的保护规则。启用合并前状态检查，从候选实际生成的检查中选择 `make check`，保留既有 PR/评审要求及限制；记录规则适用范围和绕过身份。若采用 ruleset，以实际生效规则为准。
2. 在独立测试 PR 中保留有效断言，使真实检查失败，确认合并受到阻断；恢复后确认检查成功。另验证未产生必需检查的候选同样不能合并。只读观察合并界面/接口并记录即可，不合并坏样本。
3. 由普通成员按[设计中的真实直推协议](../../openspec/changes/2026-11-04-add-skeleton/design.md#三人协作与核验顺序)执行保护探针。须证明该身份可写短分支，保留明确规则拒绝、非零退出及 main 引用未变。网络失败、无变更推送和非快进拒绝不计通过。
4. 由另一成员复核设置及上述结果，更新任务 2.5、3.5 的实际证据。PR #3 已合并时证据尚未齐备的事实作为历史偏差保留，后补验证不能改写为“首次合并前已完成”。

## 成员冷启动与最终验收

三名成员先约定同一最终提交，使用[README 冷启动](../../README.md#骨架冷启动)。每人在自己的机器记录：成员与系统、Docker/Compose 版本、干净克隆的实际提交、实际命令、HTTP 状态、版本与依赖状态、请求标识对应日志、遇阻及复测结果、另一成员的实名评审。只记录键名与脱敏结果，不上传环境文件或容器完整配置。

## 管理员一次性核对清单

| 设置位置 | 需要确认的内容 |
| --- | --- |
| Settings → Branches / Rules → Rulesets | 规则覆盖 main；要求 PR、至少另一成员一次批准；禁止强推和删除，核对管理员及应用的绕过范围。 |
| main 的必需状态检查 | 选择实际生成的 make check；开启合并前要求通过，实测失败和缺失检查均阻断。 |
| Collaborators | 三名成员的开发权限；课程任课教师无需邀请，只查看公开内容。 |
| Settings → Actions → General | 允许当前固定版本的工作流 Actions 运行；如有首次贡献者工作流等待审批，由管理员审批。工作流只需 contents: read，不因此授予作业仓库写权限。 |
| GitHub App 安装授权 | 当前连接对本仓库创建 Git tree 返回 403。确认仓库在授权范围内；发布源码需要 Contents 写入，修改 .github/workflows 还需要 Workflows 权限，创建 PR 需要 Pull requests 写入。用户自身 push=true 不代表应用已获得这些权限。 |
| 本机 Git 推送身份与网络 | HTTPS 到 github.com:443 超时，本机没有 SSH 身份。可恢复 GitHub 网络连通并配置本机 Git 登录，或修复上述应用授权；不向聊天发送令牌、口令或私钥。 |

管理员自己操作 main 保护即可，不需要为了设置规则而给助手长期管理员权限。GitHub 官方说明：[保护分支](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches)、[应用权限](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app)。
