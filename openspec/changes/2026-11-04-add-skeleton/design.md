# 第 7 课开发骨架设计

## Context

[运行骨架](proposal.md)已合入主干。后续业务可以在同一个 Flask 工程中加入路由、服务和持久化逻辑，直接复用 Compose 和检查入口。

## Goals / Non-Goals

目标是让组员能启动相同的依赖环境、找到业务接入点、修改应用并查看结果。MySQL 与 Qdrant 在骨架阶段提供连接和就绪检查。业务表、索引集合、真实用户、身份签发和教学流程由对应业务变更建立。

## Decisions

### 一、Flask 分层与显式授权

在 `app/` 内用应用工厂作装配入口，路由层处理 HTTP、输入和响应，业务服务处理授权范围与就绪聚合，仓储和外侧适配器负责 MySQL、Qdrant 实际探测；依赖由装配层注入。路由不直连依赖，业务层不导入 ORM 或外部客户端。使用统一前置检查按匹配到的路由和方法查询授权声明，关闭隐式静态和自动 OPTIONS 入口。业务装配可通过 `public_routes` 显式登记 `(endpoint, route_rule, method)`，默认仍只公开探针，别名和其他方法不继承例外。SQLAlchemy 仅可在 `app/adapters/` 中使用，待首个业务变更引入锁定依赖、仓储和版本化迁移。先初始化请求标识，再处理 HTTP 错误和授权，使 404、405 和拒绝也能关联日志。应用默认装配无可用身份来源；后续业务接入以当前数据库身份为准，接口检查功能权限，业务服务负责按资源校验归属、限制查询范围，并在写前完成校验。隔离测试注入身份来源和合成资源，正式装配不接受测试身份头、环境开关或透传权限。采用集中检查以避免逐路由手动调用造成遗漏。依据 BE-01–04/05、SEC-01–04。

### 二、锁定构建、外置配置和双探针

多阶段 Dockerfile 按已审阅的版本和摘要构建，锁定 Python 依赖与测试工具，运行层仅含应用及生产运行依赖。Compose 管理应用、MySQL 8、Qdrant 的内部网络、各自独立卷和健康检查，默认仅在宿主回环发布应用端口。容器的进程健康用 `/live`；README 的启动验收和接流量判断使用 `/health`。MySQL 用应用账号做带超时的只读探测（如 `SELECT 1`），Qdrant 通过带认证的只读探测验证可达，不创建集合。仅 `/health` 采样依赖，按有界截止处理连接和读取，限制探测并发资源，慢探测不得独占存活处理能力。核心未就绪或排空时，就绪探针停止报告可用，部署入口据此撤流。普通业务请求不调用健康探测，业务依赖按各自契约处理。排空信号独立于探测结果，应用仍拒绝新的已授权或显式公开业务请求。依赖中断保留进程以便恢复和诊断。按 OPS-01–06、BE-11 验收。

| 配置 | 入口与约束 |
| --- | --- |
| `MYSQL_HOST`、`MYSQL_PORT`、`MYSQL_DATABASE`、`MYSQL_USER`、`MYSQL_PASSWORD` | 应用必需；端口为 1–65535，启动诊断仅给键名；Compose 注入内部主机/端口及外部库名、账号、口令 |
| `MYSQL_ROOT_PASSWORD` | Compose 初始化 MySQL 必需；只传数据库容器，应用使用单独账号 |
| `QDRANT_URL`、`QDRANT_API_KEY` | 应用必需；URL 为 HTTP(S) 基址，Compose 注入内部地址，密钥由外部提供并传给向量服务 |
| `APP_HOST_PORT` | Compose 宿主应用端口，可选；在 README 登记默认 8000 和端口冲突处理 |
| 版本元数据 | 构建时由实际源提交标识注入并持久化在制品中，部署不通过环境覆写；缺失或空白按启动失败处理 |

`.env.example` 只含操作者需要提供或可调整的 `KEY=` 行，内部连接默认值在 README 单列。私有值通过未跟踪环境配置注入；构建上下文、Compose 输出、日志、测试报告和镜像检查不得暴露原值。启动时只校验配置形状和构建标识，依赖暂未就绪由探针报告。应用与运行服务器的请求日志都须符合 JSON 契约，关闭会记录原始请求行的重复访问日志。

### 三、开发与合并检查

日常开发沿用 [README 快速开始](../../../README.md#开发者快速开始)。首次启动全套服务，修改应用后按需仅重建应用，继续使用现有 MySQL 和 Qdrant 数据卷。每组实现按本组场景执行适用的单元、接口及真实依赖集成测试，在交付时保存与实际提交对应的结果。默认严格校验全部活动变更和现行主规格，显式指定 CHANGE 时再检查该变更确实可校验。合并检查仍由 GitHub Actions 调用同一个 `make check`，便于本地定位与 CI 对照。

## Risks / Trade-offs

- 容器进程先于依赖就绪 → 首次启动以 `/health` 和依赖状态确认可用。
- 开发者有未提交改动 → 日常迭代使用本地镜像标识，干净源码复现使用真实提交号。
- 业务能力逐步接入 → 骨架只提供应用工厂、依赖和通用接口，各业务变更自行定义持久化和页面。

## Migration Plan

从已验证的主干基线开始开发。优先在现有路由、服务及适配器分层中接入首个业务变更，再按该变更安排数据库迁移和数据验证。仓库保护和回滚的既有证据，以及成员复现、课程评审和归档进度，在[课程验收页](../../../docs/lesson-07/acceptance.md)记录。

核心功能齐备后使用一个候选版本做跨功能验证，见[最终验收设计](../2026-11-04-project-final-acceptance/design.md)。
