# 最终验收设计

## Context

骨架已提供 Flask、MySQL、Qdrant 和统一检查入口。认证、资料入库和检索已有规划，其他教学流程的验收依据随各自业务规约确定。最终验收以批准纳入交付的核心功能及一个可追溯的候选版本为输入。

## Goals / Non-Goals

确认候选可从干净环境启动，教师和学生能完成跨功能主流程，并取得真实、可复核的交付结论。业务缺陷修复走对应实现变更。发布、归档和标签按各自授权办理。

## Decisions

### 两个阶段的验证责任

| 阶段 | 执行与证据 |
| --- | --- |
| 实现变更 | 实施人按本变更规约执行适用的单元、接口、真实依赖集成及必要页面走查。覆盖正常、失败和边界，按仓库规则运行合并门禁及适用的模型评测、迁移检查。留存对应提交、命令、退出码和评审结果。 |
| 最终验收 | 验收人在一个隔离环境，用同一候选提交和制品运行跨功能场景。复用已具备的单项证据，核对同一候选的集成结果，按发布范围记录通过、失败、未执行、不适用和人工评审。 |

选择一个候选贯穿最终验收，避免拼接多个版本的通过结果。核心能力未齐或缺实现证据时登记缺口，交回对应变更补齐。第 7 课的启动与回滚证据继续在课程内留存，可供最终验收复用。

### 候选的可观察结果

| 前置条件 | 操作 | 可观察结果 |
| --- | --- | --- |
| 干净环境、锁定配置和制品可用 | 按 README 启动并请求就绪接口 | 报告候选版本，核心依赖可用，日志可用请求标识关联。配置或核心依赖缺失时记录原因与实际状态。 |
| 两个合成班级及师生账号已就绪 | 教师创建章节并录入资料，学生按章节检索、提问并回查引用，再提交一条无证据问答的未解决反馈 | 同班学生可追溯到原文；无证据时明确提示、无出处，教师能凭学生主动填写的说明处理反馈。跨班与不存在的资料按业务规约返回结果。 |
| 题库、测验和反馈功能已纳入候选 | 教师生成或手工建立候选题、审核并发布，学生保存草稿、正式提交并在开放后查错题，教师核对看板 | 未审核题不能发布，重复和截止后提交被拒；开放后可查答案、解析、出处和错题；看板提交率、平均分和各题正确率与冻结样本的手算一致。 |
| 模型不可用，已有本班资料和发布测验 | 教师手工建题，学生对已发布测验正式提交并等待评分 | 模型依赖错误清晰可见，人工建题、资料浏览、作答及确定性评分继续运行。 |
| 冻结评测集及配置已就绪 | 核对不少于 30 题的三路检索与回答评测，关联候选版本及配置 | 分别记录 Hit@5、回答依据充分率、无答案正确率、检索及问答中位数和 P95，以及差距与失败样本。 |
| SSE 按已核定的配置达到在途上限 | 继续发起流式请求，并同时登录、读资料、提交测验和调用探针 | 超额流快速拒绝，短请求和探针仍可用；按 OPS-11 验证短请求时延并记录资源释放。 |
| 验收场景出现失败 | 登记对应候选、输入、预期、实际和修复归属 | 必需场景保持失败状态，修复后在新的候选上复验相关链路并关联原记录。 |

## Risks / Trade-offs

- 候选版本变化会使部分证据失效 → 重新登记候选并复验受影响链路。
- 外部模型或基础设施不可用 → 单列环境故障和未执行项，保留复测结果。
