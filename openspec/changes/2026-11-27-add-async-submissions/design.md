# Design

## Context

现有 `POST /api/v1/quizzes/{quiz_id}/submissions` 在一次 MySQL 事务内校验学生、测验、草稿和截止时间，随后写入 `quiz_submissions`、`quiz_results` 与审计并返回 `201`。唯一提交、幂等指纹、答案开放、教师改分和统计已经建立，不能因异步化削弱。现有 Kafka 任务服务面向教师候选题，包含模型、证据和不同授权边界；正式交卷只需要确定性规则评分，并要求 Kafka 或模型故障时继续可用。

## Goals / Non-Goals

**Goals:**

- 把“请求已持久受理”和“正式提交已评分”分开，同时保持原有单次提交和事务评分不变量。
- 提供真实持久的本人三态、租约恢复、等价重放和刷新恢复证据。
- 让旧页面和 API 使用者以最小字段变化迁移到 `202` 与轮询。

**Non-Goals:**

- 不把规则评分改成模型评分，也不引入人工评分队列。
- 不复用教师候选题 Kafka topic、任务权限或七列技能审计冒充学生提交。
- 不改变答案开放时间、教师改分优先级、错题派生和统计公式。

## Decisions

### 用 MySQL 任务表作为受理事实

新增只增表 `quiz_submission_jobs`，保存任务 ID、预分配提交 ID、班级/测验/学生、幂等键和指纹、冻结作答、草稿修订、状态、尝试次数、下一次执行时间、租约令牌/期限、稳定失败码及各阶段时间。受理事务锁定当前学生的测验参与关系和草稿，执行全部同步校验后只写任务；响应返回 `202` 和任务地址。

预分配 `submission_id` 让现有客户端继续获得稳定标识，但在任务成功前不向 `quiz_submissions` 写入，也不计入教师汇总。替代方案是先写正式提交再异步评分；这会让未评分行进入现有统计和错题查询，并破坏“正式提交与评分同事务”的既有安全断言，因此放弃。

### 独立数据库 worker 处理规则评分

新增应用镜像内的 submission worker，以短事务领取到期 `pending` 或租约过期的 `running` 任务。领取后使用令牌条件更新；完成事务再次核对任务归属、测验和冻结参与关系，以任务的 `accepted_at` 判断截止前受理，在同一事务写入原有正式提交、规则评分、提交审计并把任务置为 `succeeded`。已有提交且标识、学生、测验和指纹完全一致视为恢复成功；任何不一致进入稳定失败，不覆盖现有结果。

worker 使用 MySQL 轮询和有界退避，单独运行于 Compose 服务，不依赖 Kafka、Qdrant或模型。这样保留课程要求的真实异步与可恢复性，同时避免为确定性小任务引入第二套 broker 契约。替代方案是投递现有 Kafka；broker 故障会把正式交卷从可选依赖变成硬依赖，且数据库受理与消息发布需要额外 outbox，收益不足。

### 同一路由切换为 202，并保留响应核心字段

提交路由继续接收现有请求体和 `Idempotency-Key`，成功响应保留 `submission_id`、`accepted_at`，新增 `task_id`、`status`，设置 `Location: /api/v1/submission-jobs/{task_id}`。完全等价重放始终返回相同对象；若任务已失败，等价重放在同一行上清理安全失败码并重新排队。任务读取仅允许当前学生本人，外班、他人与不存在同构。

`GET /api/v1/quizzes/{quiz_id}/my-submission` 在正式提交尚未成功时返回 `submitted: false` 和最小 `submission_job` 投影，供页面刷新恢复；成功后沿用现有正式提交投影。页面在收到 `202` 后轮询 `Location`，显示待处理、处理中、已完成或失败，终态停止，失败只允许以原作答和原幂等键重新排队。

保留旧 `201` 同步路由作为并行兼容入口会使同一资源产生两套提交时序，也无法确保课程自动验收走到异步能力，因此采用一次契约迁移，并同步仓库内所有客户端、OpenAPI和回归。

### 状态、租约和失败分类保持有界

公开状态为 `pending`、`running`、`succeeded`、`failed`。每次领取生成随机租约令牌；只有持有当前令牌的 worker 能完成或退避。可重试数据库故障不消费业务失败结论，任务按固定短退避重回 `pending`；超过有界次数进入 `failed/dependency_exhausted`。授权或数据不变量变化进入脱敏 `failed/resource_changed`，不泄露具体资源。完成后清空作答任务副本或按既有教学数据留存期同步清理，正式作答继续由原表保存。

### 审计区分受理和正式完成

受理不写现有 `submitted` 审计，避免把未完成任务当作正式提交。worker 成功事务继续写唯一 `submitted` 事件；任务自身的状态时间提供受理和处理证据。任务读取、失败和重放进入现有结构化请求日志，内容不记录作答、Cookie、幂等键或租约令牌。

## Risks / Trade-offs

- [HTTP `201` 改为 `202` 会影响严格检查状态码的旧客户端] → 同步更新仓库内页面、浏览器脚本、OpenAPI和集成调用；保留核心响应字段并在 README 明确迁移。
- [受理成功后 worker 暂停会延迟正式提交] → 任务已持久保存受理时间，页面显示真实状态；启动、健康与验收环境必须运行 worker，并提供积压与最老任务指标。
- [答案副本同时存在于任务和正式提交] → 任务表沿用私人教学数据权限与留存，成功事务清空任务作答字段；失败任务按留存清理，不写日志或审计正文。
- [worker 完成时账号或测验状态变化] → 再次核对班级和冻结参与关系；截止判断使用可信受理时间，归属变化失败关闭且不生成正式提交。
- [并发集中提交增加 MySQL 锁竞争] → 锁粒度限定单个测验参与者和单任务，worker 批量有上限；用真实 MySQL 集中提交回归核对吞吐和唯一性。

## Migration Plan

1. 在合成空库、现有旧库和重复升级路径应用只增迁移，先部署能识别任务表但尚未受理新任务的应用与 worker。
2. 同一候选启用异步提交入口，确认 worker、积压指标、三态页面和 `202` OpenAPI；排空观察后进入候选冻结。
3. 回退时先暂停新受理，等待 `pending/running` 排空；若新 worker 不可用，恢复同版本 worker 完成任务。旧应用只读取 `quiz_submissions`，可以忽略保留的新任务表；生产不物理降级或删除未完成任务。
4. 合成隔离库演练升级、处理中断、恢复、应用回退和物理降级；记录任务、正式提交及统计在每一步的可见性。
