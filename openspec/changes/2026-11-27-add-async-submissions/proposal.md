# Proposal

## Why

现有学生正式交卷在单个请求内完成规则评分并返回 `201`，无法满足第 10 课要求的 `202` 受理、任务标识和 `pending → running → succeeded` 可观察过程。候选题异步任务属于教师建题流程，不能证明学生作业提交具有同样的持久受理、本人轮询和失败恢复能力，因此须在最终候选冻结前补齐独立闭环。

## What Changes

- **BREAKING**：现有 `POST /api/v1/quizzes/{quiz_id}/submissions` 从同步 `201` 改为异步 `202`，继续保留 `submission_id`、`accepted_at` 和幂等键语义，同时返回任务标识、当前状态及 `Location`。
- 增加仅本人可读的提交任务查询，公开 `pending`、`running`、`succeeded`、`failed` 及安全的失败结果；学生页面受理后轮询，终态停止，刷新后可恢复当前任务。
- 使用 MySQL 持久任务把截止前受理与后台规则评分分开；任务重试不重复交卷或评分，进程退出后的租约恢复可继续处理，Kafka、模型及候选题 worker 不成为正式交卷依赖。
- 保持现有草稿修订、冻结名单、单次正式提交、班级隔离、答案开放和教师改分边界；只有 `succeeded` 的正式提交进入教师汇总、错题和统计。
- 增加只增迁移、任务 worker/恢复入口、OpenAPI 与页面状态、真实 MySQL 并发/故障/恢复、浏览器三态及安全回归，并同步课程差异和交付证据。

放弃把教师候选题任务改名为学生作业任务的方案，因为两者的身份、资源、写入结果和失败语义不同。也放弃仅在同步交卷外包一层伪轮询的方案，因为请求返回时评分已经完成，无法提供真实的持久异步状态与恢复证据。

## Capabilities

### New Capabilities

- `async-submission-jobs`: 学生正式交卷的持久受理、本人任务三态、后台规则评分、幂等与故障恢复契约。

### Modified Capabilities

无。现有 `async-quiz-submissions` 仅存在于尚未同步到主规格的历史变更中；本变更用独立能力记录对当前 `201` 行为的替换，避免把教师候选题任务视为等价实现。

## Impact

影响教学提交 API、教学服务与仓储、数据库迁移和后台运行入口、学生测验页面、OpenAPI、场景映射、Compose/候选构建以及最终验收文档。新增数据只保存受理所需的本人作答快照、状态、租约和脱敏错误码，不引入新的外部服务；旧应用不能识别新任务表和 `202` 响应，回退时保留表数据并暂停新任务受理，先排空或恢复已受理任务。
